# EYAS Memory Subsystem — Research Synthesis
*Compiled 2026-09-03 from 8 adversarially fact-checked research lenses. Refuted claims are corrected inline; claims the fact-checkers could not confirm are marked **[unverified]** and should not be treated as settled before implementation.*

## 1. Executive summary

Across all eight lenses, the 2024-2026 agent-memory literature converges on a small, recurring set of architectural patterns, and — notably — EYAS's existing hybrid design (working/episodic/archive DB tiers + a markdown vault) already sits close to where the field has landed independently. The following eight patterns are dominant, each with direct supporting evidence:

1. **Tiered/layered memory (hot in-context → warm searchable → cold immutable raw).** Nearly every serious system arrives here independently: Letta/MemGPT's core (in-context blocks) / archival (vector store) / recall (message search) / filesystem (Jul 2025 addition, grep/open/semantic_search tools) split (Apache-2.0, arXiv:2310.08560); MemOS's L1 Traces / L2 Policies / L3 World Models hierarchy (Apache-2.0, arXiv:2505.22101); CoALA's working/episodic/semantic/procedural taxonomy (arXiv:2309.02427, the reference taxonomy as of 2026); Zep/Graphiti's episodes/entities/facts (Apache-2.0, arXiv:2501.13956). This is convergent, not coincidental, evidence for EYAS's own tiering.

2. **Append-only write, retrieval-time intelligence — not LLM-mediated inline consolidation.** Mem0's own migration (Apache-2.0, github.com/mem0ai/mem0) from a two-call ADD/UPDATE/DELETE/NOOP write-time pipeline to a single-pass, ADD-only extraction model — confirmed as Mem0's *current* documented behavior, though the specific "April 2026" dating of the change is **[unverified]** (no dated changelog entry was locatable) — pushes complexity (entity linking, temporal reasoning, BM25+vector fusion) to retrieval time instead. This is directly and independently confirmed as current Mem0 behavior by two separate lenses. It validates EYAS's planned write/consolidate split, though — as discussed in §9 and §10 — EYAS should reject the *governance* implications of Mem0's newest pivot (letting agent-generated facts land as equal-weight truth) even while adopting its append-only shape.

3. **Bi-temporal, invalidate-don't-delete provenance graphs.** Graphiti (Apache-2.0, github.com/getzep/graphiti, ~30.6k stars) models memory as immutable Episodes (raw provenance) → Entities → Facts/Relationships carrying explicit `valid_at`/`invalid_at` validity windows; contradicted facts are invalidated, never deleted or overwritten. Verified benchmark figures: Deep Memory Retrieval 94.8% (Zep) vs. 93.4% (MemGPT), and up to 18.5% accuracy improvement with up to 90% latency reduction on LongMemEval (arXiv:2501.13956, confirmed verbatim by two independent fact-checks). This is the single most reusable *data model* for R5.

4. **Sleep-time / offline consolidation as first-class architecture, not a bolt-on cron job.** Letta shipped "sleep-time compute" in v0.7 (2025): the live agent can read memory but has no tools to edit core memory; a separate asynchronous agent is the sole writer during idle periods, confirmed via Letta's own blog and docs. This dual-agent read/write split is the direct precedent for a scheduled, EYAS-owned consolidation job — but EYAS must replace Letta's "second live agent" with deterministic, EYAS-orchestrated code per R2 (see §9).

5. **Recency × importance × relevance retrieval scoring.** Generative Agents (Park et al., Stanford, arXiv:2304.03442) supplies an exact, fully-verified formula: `score = recency + importance + relevance` (min-max normalized, α=1 each), recency = exponential decay at 0.995/simulated-hour, importance = a one-time LLM 1-10 salience rating at write time, relevance = embedding cosine similarity. The paper's reflection mechanism (trigger on cumulative importance ≥150, synthesize higher-level insights citing back to source records, forming a tree) is a directly implementable episodic→semantic promotion algorithm.

6. **Collapsed-tree, multi-granularity retrieval over a single index.** RAPTOR (MIT-licensed, github.com/parthsarthi03/raptor, arXiv:2401.18059) recursively clusters and summarizes bottom-up, then pools every tree level — raw chunks and every intermediate/root summary — into one flat retrieval index, letting one similarity search naturally return whichever granularity best matches a query. This is the concrete mechanism for keeping R1's token budget flat regardless of total memory size: tag every consolidation level with a depth field in the same Orama/SQLite index rather than building a separate "walk the tree" query path.

7. **Provider-side convergence on client-owned, file-based memory primitives — with a sharp split between transparent API surfaces and opaque consumer products.** Anthropic's memory tool (`memory_20250818`), context editing, and compaction (`compact_20260112`) all give the *developer's own infrastructure* ownership of storage — the model just issues tool calls (view/create/str_replace/etc.); Anthropic never stores or sees the backing files (confirmed verbatim from platform.claude.com docs). xAI's Responses API is documented as stateless by design — no server-side conversation memory, only a client-owned encrypted context-compaction blob explicitly stated not to create persistent memory (docs.x.ai, confirmed). Yet every major **consumer** product studied (claude.ai Memory, ChatGPT Memory, Gemini Personal Context, Microsoft Copilot Memory, GitHub Copilot Memory, Claude Code's own Auto Memory) lets the *model* decide what gets written — the opposite of R2. This split (transparent API contract vs. opaque consumer feature) is itself one of the clearest signals in the whole research set.

8. **Context Rot: long context is not a substitute for structured memory.** Chroma's empirical study (trychroma.com/research/context-rot, confirmed) evaluated 18 leading LLMs and found accuracy degrades non-uniformly with input length even on trivial retrieval tasks, a single distractor measurably hurts accuracy, and — the most counter-intuitive finding — shuffled/incoherent context consistently *outperformed* coherent, logically-ordered context across every model tested. This directly validates R1's premise: growing context windows do not obsolete the need for curated, tiered, ranked memory.

Taken together, these patterns describe roughly 80% of an EYAS memory architecture already implicit in prior art. The genuinely novel engineering work EYAS must do itself is concentrated in three places where no surveyed system offers a ready answer: (a) making the bi-temporal/tiered model work fully embedded on SQLite rather than an external graph database, (b) R2's write/read sovereignty as a deliberate, load-bearing divergence from every consumer product studied, and (c) R6's bidirectional, opt-in, multi-instance sync, for which — per every lens — no existing system (Mem0, Zep/Graphiti, Letta, Honcho, MCP, A2A) has a documented precedent.

## 4. Grok memory, and comparison tables

**xAI's developer API is confirmed stateless by design.** The Responses API has no server-side conversation/memory primitive: multi-turn prompt caching is keyed by a client-supplied `x-grok-conv-id` header (a cost/latency optimization, invalidated by any edit to earlier messages, no persistence-beyond-session guarantee), and context compaction returns an opaque, encrypted `encrypted_content` blob the client must store and replay verbatim — xAI's own docs state this explicitly "does not create persistent memory." This is the strongest available cross-vendor confirmation that even a frontier-model provider itself does not put memory ownership at the API layer.

**Grok Build** (xAI's own CLI agent) and the independent open-source **grok-cli** (MIT, github.com/superagent-ai/grok-cli) both converge, independently, on the same pattern already used by Claude Code: a markdown instructions file (recognizing `AGENTS.md`, `CLAUDE.md`, and variants — merged root-to-cwd, deeper files winning on conflict) for durable procedural memory, plus a separate resumable session-transcript store on disk (`~/.grok/sessions/`, resumable via `/resume`, `--resume`, `--fork-session`). Neither solves tiered/gisted memory — both are flat resumable transcripts, confirming EYAS still needs its own consolidation layer regardless of which CLI backend is active.

**Grok's consumer memory feature (grok.com/X) is almost entirely unverifiable in this research pass** — help.x.com and x.ai returned 403/blocked, and web search was exhausted. What is confirmed: grok.com has Personal/Team Workspaces with scoped sharing, and a Data Controls surface with generic retention-window language ("deleted chats and files are removed within standard retention windows unless legally required otherwise"). The specific launch date, per-item view/delete UI, and any "forget this chat" control are **[unverified]**.

## 5. Obsidian / PKM logic — primitives worth borrowing

EYAS's existing hybrid design (SQLite/Drizzle DB tiers + markdown vault) mirrors where the whole PKM industry has converged: plain, addressable files carrying structured frontmatter, with links (not folders) as the primary organizing relation, and a queryable database layer built *on top of*, never *replacing*, the files.

- **Atomic notes / Zettelkasten** (public-domain methodology): one memory = one linkable, addressable unit with a stable ID, connected by explicit links rather than folder hierarchy. Direct justification for EYAS's memory-record granularity.
- **Frontmatter/Properties** (Obsidian core, free): typed YAML metadata (project/task/tags as first-class fields) synced into Drizzle columns for filtering — the direct template for R4's tagging schema.
- **Links + backlinks over hierarchy**: every memory note should carry explicit `relates_to`/`derived_from`/`part_of_conversation` links, rendered as a backlinks panel per memory/project in the management UI — reimplemented in EYAS's own DB, never depending on a live Obsidian install (one-way import only, per the existing sovereignty constraint).
- **MOC (Map-of-Content) index notes**: a small, auto-maintained per-project/topic note listing+one-line-summarizing its children — the literal implementation of R1's "gist" layer, injected by default while full atomic notes stay a drill-down away.
- **Obsidian Bases** (free core plugin, added 2025, confirmed): computes table/list/card/map views *live* over frontmatter with **no separate database** — all data stays in plain files, views are formulas/filters, never edits to source truth. This is the exact template for R5: gists/rankings should be regenerated, non-destructive *computed views* over an immutable atomic-note tier, never rewrites of the source.
- **PARA** (Forte, public methodology): Projects/Areas/Resources/Archives as a shallow top-level taxonomy — maps directly onto EYAS's project/task tags plus an archive tier for aged-out gists.
- **Progressive Summarization** (Forte): layered, non-destructive compression (raw → bold → highlight → executive summary), applied *opportunistically* only to notes that get revisited rather than uniformly on a schedule — directly informs R5's audit-priority allocation (spend consolidation effort where memories are actually reused, per Forte's "opportunistic compression" principle, paired with a cheap reuse-frequency signal).
- **Johnny.Decimal**: a bounded, human-legible `area.category.id` addressing scheme — a candidate for stable, short, cross-instance memory IDs for R6's shared-memory design.
- **Evergreen notes** (Andy Matuschak, essay/technique — full criteria text is **[unverified]** from primary source in this research pass, though the "iteratively rewritten as understanding improves" framing is well-established): the conceptual basis for gists being re-derived and improved by each audit pass while the underlying transcript stays untouched.
- **Smart Connections**: proof that fully local, no-API-key vector embedding search over a plain-file note store is practical today, validating EYAS's own no-external-service Orama/sqlite-vec plan. **Note on license:** Smart Connections is source-available under the "Smart Plugins License" — permits use/modification but restricts building a competing Obsidian product; it is **not** OSI-approved MIT/BSD, so EYAS can only take the *design pattern*, never vendor its code.
- **mcp-obsidian** (MarkusPfundstein, MIT, 4.4k stars, 498 forks, confirmed): the clearest concrete evidence that "vault as agent memory over MCP" is now a mainstream 2025-2026 integration pattern — and, notably, two Obsidian-facing MCP servers are attached to this very research session, direct first-hand confirmation. Its *write* tools (append/patch/delete, agent-driven) are exactly the anti-pattern R2 rejects; EYAS should expose analogous **read** tools while keeping all writes EYAS-only.

**Corrections applied to two previously-hedged license claims:**
- **Dendron** is confirmed **Apache-2.0** (not "unverified" as one lens hedged), and its own README carries an explicit notice: *"Dendron is currently in maintenance only, active development has ceased"* — not merely "community reports suggest slowed maintenance." Its dot-hierarchy-in-filename addressing (`aws.ec2.quickstart`) remains a usable idea regardless of the project's own maintenance status.
- **Anytype** is confirmed to ship under the **"Any Source Available License 1.0"** — a source-available license, **not** MIT-compatible/OSI open source (previously reported as fully "UNVERIFIED"). Its local-first, P2P, end-to-end-encrypted "any-sync" architecture is a legitimate sovereignty-aligned design reference, but the code itself cannot be vendored under EYAS's MIT-compatibility policy.

**Explicit anti-pattern to design against:** Obsidian Copilot and Smart Connections' agentic write mode both let an AI agent read *and* write the vault directly and autonomously — this is precisely the write-side pattern R2 forbids; borrow the embedding/retrieval mechanics, never the autonomous-write authority.

## 6. Shared multi-instance memory (R6) — protocol options and recommendation

No lens found an existing system that solves R6's actual shape: 10-15 independently-run, self-hosted EYAS instances syncing an opt-in, per-project/per-tag subset of memory bidirectionally, with no central vendor. The candidates split into three unrelated camps that nobody has combined:

**(a) Hosted agent-memory platforms** solve single-tenant *scoping* well (Mem0's four identifiers — `user_id`/`agent_id`/`run_id`/`app_id`; Letta's shared memory blocks referenced by `block_ids`, with `memory_insert` append=safe, `memory_replace` CAS-style, `memory_rethink` full-rewrite=last-writer-wins, confirmed via Letta's own docs, which now recommend against building on this legacy mechanism in favor of unconfirmed "shared memory repositories") but give **no federation story** — none expose a cross-instance sync API. Zep's 2026 retreat from a self-hostable Community Edition to cloud-only (confirmed) is a concrete, dated cautionary data point against depending on any vendor-hosted "memory as a service" for R6's hub.

**(b) Agent-interop protocols explicitly exclude memory sharing from scope.** A2A's own spec text states agents "interact without needing to share internal memory, tools, or proprietary logic" (confirmed verbatim). MCP has no built-in sync primitive — its official reference "memory" server (MIT, github.com/modelcontextprotocol/servers) is a JSONL-file, in-memory-scan, no-conflict-handling demo, useful only as a naming/tool-shape convention (`create/delete entities`, `create/delete relations`, `read_graph`, `search_nodes`), not as production infrastructure.

**(c) Local-first sync engines** solve the actual bytes-over-the-wire and conflict problem, but were built for documents/rooms, not typed, tag-scoped, redactable memory records:
- **CRDTs**: Automerge (MIT, JSON-CRDT, v3 cut memory ~10x in 2026), Yjs (MIT, `y-websocket` provider = a ready hub-and-spoke topology with no external signaling dependency, unlike `y-webrtc` which needs STUN/TURN — an external-service dependency EYAS's constraints forbid assuming), Loro (MIT, v1.0, fastest/most compact of the three). All carry real per-item CRDT-metadata overhead — better suited to a small set of frequently co-edited documents (e.g. a shared project charter) than bulk fact-stream sync.
- **SQLite-native**: **cr-sqlite** (MIT, github.com/vlcn-io/cr-sqlite) — a loadable SQLite extension turning ordinary tables into CRDTs, per-column merge strategy (LWW for scalars, counters, etc.), exposing a `crsql_changes` virtual table as a natural pull-since-cursor sync source. This is the single most architecturally-aligned building block found, since EYAS already stores memory in SQLite via Drizzle — but whether `bun:sqlite`/`better-sqlite3` actually support `.loadExtension()` for it across target deployment platforms is **[unverified]** and needs a hands-on spike before committing. **ElectricSQL** (a comparable local-first Postgres/SQLite sync engine) was listed as a source by one lens but never actually discussed in its body — a real gap flagged by the fact-checker and worth independent evaluation before finalizing this choice.
- **Document-replication**: the **CouchDB replication protocol** (Apache-2.0, part of Apache CouchDB, 15+ years production) is the best available *battle-tested template*, not a dependency to adopt: MVCC revision IDs, a deterministic winner chosen on conflict while **preserving every conflicting leaf revision** (nothing silently discarded), checkpointed/resumable replication via a `session_id` log, no central coordinator required. PouchDB (Apache-2.0, ASF Incubation, browser-focused) is the JS reference implementation but not itself recommended as a dependency for EYAS.
- **Federation**: the **Matrix protocol** (open spec) is the strongest real-world precedent for EYAS's exact target shape — independently-run homeservers, no central authority, an event DAG, and a deterministic, transitive state-resolution algorithm that all servers compute independently and reach identical results from regardless of arrival order (an AP-over-C, CAP-theorem-favoring design). Adopting the full Matrix stack is too heavyweight; the *state-resolution principle* is the right correctness bar to implement inside a lighter scheme.
- **File sync**: **obsidian-git** (MIT) validates git-object-based, whole-file, three-way-merge-on-conflict sync as the right mechanism specifically for the **markdown vault tier** — prose should never undergo automatic text-CRDT merging. **Syncthing** (confirmed **MPL-2.0**) is a legitimate optional, user-run companion for vault-folder mirroring, but explicitly out of scope for the structured, tag/ACL-scoped memory tier (BEP has no concept of per-tag ACL, redaction, or provenance).

**Access control and capability tokens**: **node-casbin** (Apache-2.0, pure JS/TS, embeds directly in Bun with no sidecar, ABAC/ReBAC-capable) is the recommended engine over OpenFGA (Apache-2.0 but Go-only embedding, would require a sidecar process, cutting against EYAS's single-process posture). **Biscuit tokens** (Apache-2.0, Eclipse Foundation, offline-attenuable capability tokens with a Datalog policy body, Rust/WASM/JS bindings) are the recommended per-share mechanism — a token scoped to `project:X, tags:[a,b], expires:<date>` can be further restricted and re-forwarded by a recipient without contacting the issuer, and verified fully offline; a simpler signed-JWT fallback loses attenuation and true offline revocation-checking if the Biscuit toolchain proves too heavy.

**Redaction**: Microsoft Presidio (MIT, confirmed) is the right reference implementation to copy the *pattern* from (NER + regex + checksum validators, explicit disclaimer of incomplete recall) — it is Python-only with no first-party TypeScript port, so EYAS must hand-roll an equivalent TS scanner and pair it with a mandatory, human-reviewable redaction-preview step in the R3 UI before anything crosses an instance boundary.

**Recommendation.** Match EYAS's existing two-tier architecture with two matched sync mechanisms, exposed over a single MCP server (`eyas-memory-share`) with a small, versioned tool contract (`push_since(cursor, scope)`, `pull_since(cursor, scope)`, `list_shared_scopes()`, `revoke_scope(scope)`):
1. **Structured DB tier** (working/episodic/archive rows): per-row `(physical_ms, logical_counter, origin_instance_id)` hybrid-logical-clock stamp + tombstone flag, field-level last-writer-wins on conflict — the cr-sqlite/CouchDB pattern, hand-rollable directly as Drizzle columns if the extension-loading path proves unreliable.
2. **Markdown vault tier** (semantic/procedural notes): whole-file, content-hashed git objects synced via a plain git remote (obsidian-git's pattern) — free history/audit trail via `git log`, no CRDT complexity for prose.
3. **Topology**: hub-and-spoke, not P2P — one self-hosted EYAS-like process (or a small dedicated relay, still self-hosted) elected per team, avoiding the STUN/TURN/signaling dependency P2P CRDT sync would require.
4. **ACL**: node-casbin, ABAC keyed on the same project+tag metadata R4 already requires — reusing R4's tagging system as the sharing boundary rather than a parallel permission taxonomy.
5. **Revocation**: non-destructive — unsharing broadcasts a tombstone/scope-revoked event; spokes move previously-synced items into a quarantined "revoked-shared" archive layer, never silently deleted, preserving R5's audit-first stance even across a trust boundary.

**Unresolved gaps flagged explicitly by the fact-checkers** (see also §11): how two instances reconcile *different* gists generated for the same underlying shared conversation (no surveyed system addresses gist-level, as opposed to fact-level, merge); unbounded tombstone growth over a long-lived shared store (garbage-collection/compaction was not addressed by the design); whether the hub itself needs encryption-at-rest beyond the pre-share redaction gate; ElectricSQL's unevaluated fit.

## 8. Governance model — layers, rules, and memory-poisoning mitigation

The 2025-2026 literature converges on one structural idea, borrowed from software architecture rather than AI research: **Event Sourcing** (Fowler, martinfowler.com/eaaDev/EventSourcing.html, confirmed) — keep an immutable, append-only raw layer as the sole source of truth, and treat everything above it as a rebuildable *projection*. Concretely, for EYAS:

**L0 — Raw/immutable, append-only (event log).** Every ingested message/tool-call/document is written once, with a monotonic id, source, timestamp, and actor; content-addressed by SHA-256 (automatic dedup of repeated boilerplate), zstd-compressed via Bun's native compression before storage as a SQLite BLOB. Nothing above L0 is ground truth. This is the layer R5 requires to survive every reorganization untouched.

**L1 — Derived facts, bi-temporal.** Reimplement Graphiti's column design directly on SQLite (never take Graphiti itself as a dependency — it is Python-only and requires an external graph DB, both ruled out): each fact is `(subject, predicate, object/text, valid_from, valid_until|NULL, invalidated_by_fact_id|NULL, source_episode_ids[], confidence)`. Contradiction handling = write a new fact and set `valid_until`/`invalidated_by` on the old one — **never** `UPDATE`/`DELETE` a row in place. This gives "what did we believe on date X" for free.

**L2 — Gists/summaries, RAPTOR-style collapsed tree.** Regenerated as computed projections (Obsidian-Bases-style: derived views, never destructive rewrites) by a scheduled, **EYAS-owned** consolidation job — Letta's dual-agent read/write split reimplemented as deterministic code, not a second live agent. Every gist carries provenance pointers back to its source facts/episodes plus the consolidation job-run id, so an audit view can show "gist G3 was produced by consolidation-run #482 from facts F1, F7, F19" (Generative Agents' reflection-citation pattern).

**L3 — Index/search.** Orama/SQLite FTS5+sqlite-vec is purely a rebuildable projection over L0-L2, never a second source of truth — index corruption or a schema change must never risk losing the audit trail; rebuild-from-log should be a documented, tested operation.

**Write-time gate (the R2 boundary).** The model is invoked only as a stateless extractor; **EYAS's deterministic code — not the model — decides commit/dedup/link.** This deliberately mirrors the *pre-2026* Mem0 ADD/UPDATE/DELETE/NOOP tool-call pattern rather than Mem0's 2026 ADD-only pivot: the newer pattern lets model-produced facts land as equal-weight truth with no explicit arbitration checkpoint, which is precisely the anti-pattern R2 exists to prevent, even though its *append-only* shape is otherwise a good fit. This is a deliberate rejection, not an oversight — Mem0's own field experience motivating the pivot (cost/latency at hosted-multi-tenant scale) does not apply to EYAS's governance requirements.

**Tagging (R4).** A required tag set — `project_id, task_id, entity_ids[], topic_tags[], source_type, confidence, layer` — enforced by a Zod schema at write time, stored as a normalized join table `(memory_id, tag_type, tag_value)` with a covering index, never embedded inside FTS/vector blobs, so the audit UI can facet/filter by project+task+tag independent of search relevance.

**Right-to-erasure vs. R5's "always retain the complete original."** These two requirements are in direct, unavoidable tension for any EU-facing deployment, resolved via **crypto-shredding** (Wikipedia, confirmed, explicitly linked to GDPR right-to-erasure, Apple's device-wipe cited as a real-world example): each L0 record (or a per-user/per-project key partition) is encrypted with its own Data Encryption Key (DEK) wrapped by a master key, using standard AEAD (`node:crypto`/WebCrypto — no external dependency). "Hard delete" = destroy the DEK; the ciphertext remains as inert, structurally-intact audit residue, and everything derived from it is force-invalidated (never deleted) with a tombstone `reason='key_destroyed'`. This is the mechanism that should sit behind any "delete" button in the R3 UI that a user expects to be irreversible, as distinct from an ordinary reversible soft-delete/tombstone.

**Memory-poisoning mitigations.** Two independent, high-confidence pieces of research confirm retrieval-triggered memory poisoning is a demonstrated, not merely theoretical, attack class against exactly this architecture:
- **AgentPoison** (arXiv:2407.12784, confirmed): embedding-space trigger optimization achieving >80% average attack success with <1% impact on benign performance, at <0.1% poison rate, tested against RAG-based autonomous-driving, knowledge-intensive QA, and healthcare EHR agents.
- **MINJA** (arXiv:2503.03704, confirmed): a *query-only* injection attack requiring **no privileged write access at all** — an attacker chains "bridging steps" and progressively-shortened "indication prompts" purely through ordinary interaction to get poisoned records preferentially retrieved later.

Mitigation, per the general principle in "Design Patterns for Securing LLM Agents against Prompt Injections" (arXiv:2506.08837, abstract confirmed; its **specific named patterns are [unverified]** — the full text was not retrievable and should not be cited by name without a follow-up read): separate trusted control flow from untrusted content. Retrieved memory text may influence what the model *reads and says*, but never what tools get called or what future memory gets written — no "memory writes memory" loop. Every memory row carries a source/trust tier; content from R6 sync peers, ingested documents, or non-owner message sources is marked untrusted/quarantined by default and must pass through EYAS's own independent extraction/consolidation rather than being trusted as an equal-weight fact directly.

**R3 UI, concretely.** Three linked views over the same Drizzle/SQLite tables: (1) a browsable, facetable list per tag/project (search via Orama FTS+vector), (2) a provenance/lineage view per fact — a small DAG from source episodes → extraction run → consolidation runs → current gist, (3) a read/write access log (which prompt/tool-call consumed which memory ids; which job wrote/invalidated which). Unlike every peer studied (which caps out at view+delete), EYAS should support **true edit-in-place** on the gist/summary tiers, logged as a new bi-temporal version — never as an instruction sent back to the model — while the L0 raw layer stays append-only and immutable.

**Standards the fact-checkers flagged as absent from this research and worth a follow-up look before finalizing the governance spec:** W3C PROV (PROV-DM/PROV-O) as the standard academic provenance ontology (entities/activities/agents/derivation chains) — the design above reinvents a provenance schema from the Graphiti/event-sourcing analogy without checking it against this existing standard; NIST AI RMF and ISO/IEC 42001 as formal AI-governance/audit frameworks; GDPR Article 30 (records of processing) and the broader data-minimization requirements beyond crypto-shredding's narrow erasure use case.

## 9. Requirement-by-requirement mapping (R1–R6)

**R1 — Remember everything; gist for old/large topics; low token budget at 10⁵+ items.**
Satisfied by: RAPTOR's collapsed-tree indexing (MIT) so one hybrid FTS+vector query naturally returns the right granularity; Generative Agents' recency×importance×relevance scoring (fully verified formula, cheap to implement with zero extra model calls at read time); Claude Code's Auto Memory index-first pattern (hard-capped always-injected index + on-demand topic files) as the literal L0 gist layer; only embedding the gist/entity layer (not raw messages) to keep the vector table in the low tens of thousands where sqlite-vec's brute-force scan stays cheap; Chroma's Context Rot findings as empirical proof that big context windows do not substitute for this design.
**Main tension:** the actual per-item cost (tokens + latency) of importance/salience scoring at EYAS's target scale, run via a CLI-only provider with no dedicated cheap/fast model tier, was evaluated by **no** surveyed system — this is a genuine, unresolved research gap flagged independently across two lenses. Resolve via batched/cron-scheduled scoring (sleep-time-compute style), never a per-message inline LLM call.

**R2 — EYAS owns all memory; model never decides what's stored or retrieved; model usable only as a stateless function, ideally avoided where feasible.**
Satisfied by: Anthropic's memory-tool *contract shape* (client owns all storage, model only calls read/write tools) as the clearest cross-vendor validation that this pattern is achievable with any tool-calling model; xAI's confirmed-stateless API as independent proof even a frontier vendor doesn't put ownership in itself; local ONNX embeddings (transformers.js, CPU-only) decoupling even the "stateless function" role from whichever chat provider happens to be active, satisfying the "avoid depending on the model where feasible" preference specifically for the embedding step.
**Main tension:** this is a **deliberate, load-bearing divergence from the industry default**, not an incidental design choice — every consumer/product-level competitor studied (ChatGPT, Gemini, Microsoft Copilot, GitHub Copilot Memory, claude.ai Memory, Claude Code Auto Memory, and even Mem0's and Letta's frameworks in their agent-facing modes) lets the model decide at least part of what gets written. EYAS's design documentation should explicitly frame R2 as an intentional differentiator to defend, not a gap to reconcile with prevailing practice.

**R3 — Usable, transparent management UI: search, view, edit, delete, browse layers and provenance.**
Satisfied by: Claude Code's `/memory` + `/context` split (list everything vs. debug exactly what's injected this turn) as the interaction-model template; Obsidian Bases' filterable/sortable table over frontmatter as the primary navigation at scale (never a global graph view, which is known to become unreadable past a few hundred nodes — relevant given EYAS's tens/hundreds-of-thousands-of-items target); GitHub Copilot Memory's/Guru's "verified vs. needs-review" trust-state card pattern for distinguishing "my own note" from "synced from teammate X, unreviewed" at a glance.
**Main tension:** the view+delete-only ceiling every peer reaches is not a limitation EYAS must accept — true in-place editing on the gist/summary tiers is achievable and is the concrete differentiator recommended in §8.

**R4 — Every memory labelled with project, task, and other tags; navigable audit.**
Satisfied by: Obsidian's flat+nested tag model over Notion/Tana's typed-schema model (cheap to extend ad hoc, no schema migration per new project/task — the right fit for EYAS's evolving domain); GitHub Copilot Memory's repo-scoped facts as real-world precedent for project-level visibility scoping; LangMem's namespace-per-scope pattern (MIT-licensed); MemOS's/Memori's typed-category augmentation (facts/preferences/relationships/rules/skills) as a schema template.
**Main tension:** none significant — this requirement is the best-supported by prior art of the six.

**R5 — Periodic audit/reorganization (consolidation, dedup, re-ranking, gist rewriting), with one layer always retaining the complete original.**
Satisfied by: Event Sourcing's log/projection split as the structural backbone; Graphiti's bi-temporal invalidate-don't-delete fact model, reimplemented natively on SQLite; Letta's sleep-time-compute dual-agent split, reimplemented as a deterministic EYAS scheduler job; MemoryBank/SM-2/Ebbinghaus-curve-style decay scoring for zero-model-call audit prioritization; Forte's Progressive Summarization for opportunistic, reuse-triggered compression effort; crypto-shredding to resolve the GDPR tension.
**Main tension:** Mem0's 2026 pivot is directly instructive as a **negative** example here — its move away from explicit write-time UPDATE/DELETE arbitration toward accumulate-everything is a regression from a governance standpoint that EYAS must not copy, even though the pivot is otherwise cited (correctly) elsewhere as validating an append-only *shape*. The distinction matters: append-only writes are good; removing deterministic arbitration of what counts as truth is not.

**R6 — Shared memory (later phase, designed now): per project/tag opt-in sharing; bidirectional sync between independent EYAS instances via API/MCP.**
Satisfied, partially, by: Graphiti's episode-provenance model as the natural sync unit; CouchDB's replication-protocol shape (checkpointed, deterministic-winner-preserve-conflicts) as the best battle-tested template; Matrix's deterministic, order-independent state-resolution principle as the correctness bar; Letta's three-tier write-consistency semantics for conflict handling; GitHub Copilot Memory's repo-scoped-to-write-access-users as a loose (same-vendor-only) precedent for "share by project."
**Main tension:** this is the one requirement where **no surveyed system offers a real precedent** — confirmed independently by every lens that touched it (sota-architectures, cognitive-models, shared-memory, audit-governance all state this explicitly). EYAS must originate this design rather than adapt one, and several concrete sub-problems (gist-level merge policy, tombstone garbage collection, hub encryption-at-rest) remain genuinely open even within the recommendation in §6.

## 10. Consolidated design implications

1. **Adopt a four/five-tier schema — L0 raw (immutable, append-only, content-addressed, zstd-compressed) → L1 bi-temporal facts (Graphiti column design on SQLite) → L2 RAPTOR-style collapsed-tree gists (regenerated as computed views, never edited in place) → L3 rebuildable Orama/sqlite-vec index — modeled directly on the convergent Letta/MemOS/CoALA/Zep tiering found across every relevant lens**, replacing "vector-store-only RAG" with a structured, provenance-carrying design. *Evidence: §1 pattern 1, §8.*

2. **Never let the model decide what is written or what is retrieved, on any code path — including EYAS's own consolidation job.** Model calls are stateless extraction/summarization/scoring functions only; commit/dedup/link decisions are deterministic EYAS code. This is a deliberate divergence from the dominant industry pattern, not an oversight, and should be documented as such. *Evidence: §3 (memory-tool contract shape vs. every consumer surface studied), §9 R2.*

3. **Generate a gist at write time (not only in a later batch job)**, following fuzzy-trace theory's parallel-encoding model and levels-of-processing theory: one cheap, EYAS-triggered LLM call per conversation/task close producing an importance score (1-10, Generative-Agents-style) and a 1-2 sentence gist, stored alongside the untouched verbatim record — never a per-message call at EYAS's target scale. *Evidence: §1 pattern 5, §9 R1.*

4. **Implement retrieval as Reciprocal Rank Fusion (BM25 + vector, k=60) over a single collapsed-tree index, optionally reranked by a tiny CPU cross-encoder (ms-marco-MiniLM-L-6-v2) before injecting the top 5-10 as full text**, everything else staying a one-line gist reference expandable on demand. *Evidence: §6, §7.*

5. **Compute embeddings locally via transformers.js + ONNX Runtime (quantized all-MiniLM-L6-v2, ~23 MB, CPU-only), offering API embeddings (OpenAI, Voyage) only as a strictly optional upgrade** — this is the load-bearing mechanism for making even the "model as stateless function" role fully provider-agnostic and GPU-free. *Evidence: §7.*

6. **Store all memory tiers in SQLite via Drizzle (FTS5 + sqlite-vec, co-located in one file) as the single source of truth; do not adopt Orama, LanceDB, DuckDB, or any graph database as a second storage engine for the primary store.** Keep Orama for EYAS's existing bounded search surfaces only. *Evidence: §7.*

7. **Do not adopt a persistent embedded graph database.** Kuzu — the strongest MIT-licensed embeddable candidate — self-archived on 2025-10-10 with no successor. Model entity/relationship triples as plain indexed SQLite rows and materialize an in-memory Graphology graph (MIT) on demand for traversal, discarding it after use. *Evidence: §2, §7.*

8. **Model every derived fact as bi-temporal — `valid_from`/`valid_until`/`invalidated_by`/`source_episode_ids[]`/`confidence` — with contradiction resolved by writing a new fact and invalidating the old one, never `UPDATE`/`DELETE` in place.** *Evidence: §1 pattern 3, §8.*

9. **Run consolidation as a scheduled, EYAS-owned job (never a live second agent) that only ever emits new gist/fact rows plus supersedes-links, carrying its own job-run id in provenance** — Letta's sleep-time-compute *shape*, reimplemented deterministically. *Evidence: §1 pattern 4, §8, §9 R5.*

10. **Prioritize the audit backlog with a cheap, zero-model-call decay/priority score** (SM-2-adapted or Ebbinghaus-shaped: recency-weighted, boosted on actual retrieval/reuse, reset on correction) rather than a fixed calendar schedule, following Forte's "opportunistic compression" principle. *Evidence: §5, §9 R5.*

11. **Enforce a required tag set (`project_id, task_id, entity_ids[], topic_tags[], source_type, confidence, layer`) via Zod at write time, stored as a normalized join table with a covering index — never embedded inside FTS/vector blobs.** *Evidence: §8, §9 R4.*

12. **Reject Mem0's 2026 ADD-only pivot as EYAS's write model; keep an explicit LLM-proposes/EYAS-decides gate closer to Mem0's pre-2026 ADD/UPDATE/DELETE/NOOP pattern**, with the arbitration itself performed by deterministic EYAS code rather than an LLM tool call. *Evidence: §1 pattern 2, §8, §9 R5.*

13. **Resolve the GDPR-erasure vs. "always retain the original" tension via crypto-shredding**: per-item/per-scope DEKs wrapped by a master key; "delete" destroys the DEK, leaving inert ciphertext and force-invalidated (not deleted) derived facts with `reason='key_destroyed'`. *Evidence: §8.*

14. **Build the R3 UI as three linked views (browsable/facetable list, provenance/lineage DAG, read/write access log) with true in-place edit on gist/summary tiers — a genuine differentiator, since every peer studied caps out at view+delete only.** Edits are logged as new bi-temporal versions, never sent back to the model. *Evidence: §4, §8, §9 R3.*

15. **Gate all retrieved/injected memory content as trusted-vs-untrusted at prompt-assembly time**: content from R6 sync peers, ingested documents, or non-owner sources is quarantined by default, never allowed to trigger tool calls or future writes directly, and independently re-extracted/re-consolidated locally rather than trusted as equal-weight fact. This is a direct, evidence-backed mitigation against demonstrated (not theoretical) memory-poisoning attacks. *Evidence: §8.*

16. **Design R6's sync surface now as an MCP server exposing `push_since`/`pull_since`/`list_shared_scopes`/`revoke_scope`, using a hub-and-spoke topology (self-hosted, never P2P/STUN-TURN-dependent), with two matched sync mechanisms**: HLC-timestamp+tombstone row sync (cr-sqlite pattern, hand-rollable in Drizzle) for the structured DB tier, git-object whole-file sync (obsidian-git pattern) for the markdown vault tier. *Evidence: §6.*

17. **Use node-casbin (ABAC, embeds in Bun) for per-tag/per-project sync ACLs, reusing R4's tags as the sharing boundary; issue Biscuit capability tokens (offline-attenuable) scoped per shared project/tag rather than one shared secret.** *Evidence: §6.*

18. **Build a mandatory, best-effort TypeScript PII/secret redaction scanner (modeled on Presidio's entity/recognizer list — Presidio itself is Python-only, not embeddable) as a pre-share gate, paired with a human-reviewable redaction preview in the R3 UI; never trust automated redaction alone.** *Evidence: §6.*

19. **Make revocation non-destructive: unsharing broadcasts a tombstone; previously-synced items move to a quarantined "revoked-shared" layer, never silently deleted, preserving R5's audit-first stance across the trust boundary.** *Evidence: §6.*

20. **Give every memory row a stable content-hash and HLC-style revision field from day one, before R6 ships**, so a future sync protocol needs no schema migration and can do row-level merges immediately. *Evidence: §7, §6.*

21. **Confirm two concrete engineering unknowns via a hands-on spike before committing the schema**: whether `bun:sqlite`/`better-sqlite3` support `.loadExtension()` for cr-sqlite across all target deployment platforms (bare VPS, Docker, K8s, both Bun and the Node 22 fallback), and whether `bun:sqlite`'s statically-linked SQLite ships FTS5 enabled by default on Linux — both are currently **[unverified]** and load-bearing for the storage design. *Evidence: §7, §11.*

## 11. Open questions and risks

### Genuine, cross-lens-confirmed design gaps (no existing precedent found)
- **R6's gist-level merge policy** — no surveyed system (Mem0, Zep/Graphiti, Letta, Honcho, CouchDB, Matrix) addresses how two independently-generated gists for the *same underlying shared conversation* should be reconciled once synced (keep both, vote/merge, prefer more-detailed) — this is unsolved, not merely unresearched.
- **Tombstone/version garbage collection** for any HLC+tombstone or bi-temporal scheme over a genuinely long-lived (years, 10⁵+ items) shared store was not addressed by any lens's recommendation — a well-known hard problem left open.
- **Per-item importance/salience scoring cost at CLI-only, no-API-key scale** — no surveyed system was evaluated under this specific constraint, which is EYAS's stated primary deployment scenario.
- **Behavior of every consolidation mechanism surveyed (Mem0's ADD/UPDATE/DELETE, Generative Agents' reflection-tree) at multi-hundred-thousand-item, multi-year scale** — every cited benchmark (LoCoMo ~35 sessions, LongMemEval ~500 questions) tests orders of magnitude smaller/shorter than R1's actual target.

### Technical unknowns requiring a hands-on spike, not further literature review
- Whether `bun:sqlite`/`better-sqlite3` support `.loadExtension()` for cr-sqlite on target platforms.
- Whether `bun:sqlite`'s statically-linked SQLite build enables `SQLITE_ENABLE_FTS5` by default on Linux/Docker.
- Whether sqlite-vec's `vec0` table has a production-ready ANN mode, or remains brute-force by default.
- Whether `@duckdb/node-api` is Bun-compatible.
- Drizzle ORM's actual support level for querying FTS5 `MATCH`/`rank` and `vec0` KNN via raw SQL.
- libSQL/Turso as a possible way to sidestep the bun:sqlite extension-loading gap entirely (never evaluated in this research pass).

### Facts the fact-checkers explicitly could not verify — treat as open, not settled
- The exact algorithm claude.ai uses to build its "memory summary" (continuous vs. batch) and Grok's consumer memory feature in any detail (launch date, UI, per-item controls) — largely due to 403/blocked fetches, not absence of a feature.
- The exact "April 2026" dating of Mem0's ADD-only pivot (the pivot itself, as current behavior, is confirmed; only the specific date is unconfirmed).
- ACT-R's base-level-activation equation and MemoryBank's exact Ebbinghaus-based retention formula (both flagged unverifiable from primary sources by the original researchers and not independently resolved by fact-checking).
- The specific named design patterns and formal guarantees inside arXiv:2506.08837 (only the abstract was retrieved).
- Whether Anthropic's Managed Agents Memory Stores expose any built-in semantic/vector search (the documented API surface suggests no, but this is not a confirmed negative).
- ChatGPT's "Manage memories" UI mechanics and Cursor's current possession (or not) of a distinct "Memories" feature separate from Rules.

### Topics the fact-checkers flagged as conspicuously missing from the underlying research and worth a dedicated follow-up before finalizing the design
- **W3C PROV** (PROV-DM/PROV-O) as the standard provenance ontology — never checked against the ad hoc provenance schema proposed in §8.
- **NIST AI RMF / ISO/IEC 42001** and GDPR Article 30 (records of processing) — no formal AI-governance/compliance framework was consulted; the governance design stays at a purely technical-implementation level.
- **Working-memory-capacity research** (Miller's "magic number seven," Cowan's ~4-chunk revision) and **Cognitive Load Theory** (Sweller) — both directly relevant to sizing EYAS's working-memory/context-window tier and the R1 token-budget argument, absent from the cognitive-models lens despite its otherwise thorough treatment of Ebbinghaus/ACT-R/fuzzy-trace/levels-of-processing.
- **Retrieval practice / the testing effect** (Roediger & Karpicke) — a closer cognitive-science fit than reconsolidation for the "access-triggers-re-derivation" design idea, never cited.
- **"Lost in the middle"** context-utilization research (Liu et al.) — mentioned only obliquely, never as its own finding, despite direct relevance to how retrieved gists vs. verbatim records should be ordered within an assembled prompt.
- **Microsoft's agent-memory frameworks** (Semantic Kernel, AutoGen/AG2) and **TypeScript-native agent frameworks with built-in memory** (Mastra, Voltagent) — the surveyed landscape is almost entirely Python-ecosystem, despite EYAS itself being TypeScript-native.
- **ElectricSQL** — cited as a source by the shared-memory lens but never actually discussed in its body, a real gap given its direct relevance to the R6 sync recommendation.
- **libSQL/Turso, node-llama-cpp, PGlite+pgvector, ChromaDB** — all absent from the storage-technology comparison despite being directly comparable candidates.
- **Confidence/trust-scoring mechanisms as actually implemented** in any surveyed production system (does Zep or Mem0 really expose a queryable "confidence" field the way EYAS's proposed schema assumes?) — the design implication is prescriptive, not verified against precedent.
- **User-reported failure modes** (wrong memories, stale facts, privacy complaints) for any of the products studied — explicitly sought but essentially unreachable in this research pass (most forum/news sources were blocked or unavailable).
