# EYAS Memory — Gap Analysis: Design v2 vs. the Codebase at HEAD `fc9075bd`

*2026-09-03. Read-only. Inputs: design-v2, the merged as-is inventory, the F2 open-question verification, research synthesis §9–11, and the operator's roadmap note. Every file path below is relative to `the repository root` and was re-checked in the tree unless marked [unverified]. Row counts come from a read-only query of the live `data/sqlite/eyas.db`.*

## 0. Facts that frame everything below

**The live store is tiny; the product surface is not.** At HEAD: 46 `conversations`, **61 `conversation_messages`** (34 user / 27 assistant), `episodic_memories` = `archive_memories` = `working_memory` = `memory_blocks` = `team_memory` = `tool_executions` = **0**, `vault_index` = **266** notes (264 `kind=reference`, 1 `user`, 1 `feedback`; 265 `tier=semantic`, 1 `procedural` — overwhelmingly the data-port import of the external ai-memory tree), `memory_note_links` = 2, `memory_capture_runs` = 15 (12 empty batches, 1 `error`, 1 `too-short`, 1 `unparsable`), `agent_events` = 18 (9 `LlmResponse`, 9 `CriticVerdict`), `god_mode_runs` = 4. The 335 MB database is `search_chunks` (101,328 rows), not memory. Migration risk for *this* install is therefore about correctness of the procedure, not volume; the procedure must still be written for arbitrary installs.

**`conversation_messages` is not a complete raw record today.** Only interactive user/assistant text is persisted (`src/modules/conversations/routes.ts` `chatService.addMessage` sites at 694/750/1366/1396/1452). `tool_result` events are streamed to the browser and dropped (`routes.ts:1266-1273`); `tool_executions` has zero rows; background/scheduled runs never call `addMessage` (`src/modules/agent/conversation-runner.ts:818`) — their outputs exist only as `agent_events` `LlmResponse` payloads (`src/modules/event-store/schema.ts:16`, read back by `lastRunOutput`, `conversation-runner.ts:268-280`). On CLI providers the real transcript lives in the SDK/ACP session (`conversations.sdk_session_id`), invisible to EYAS except through stream events. Design v2's L0 ("every message, tool call/result, and ingested-document chunk, verbatim") therefore needs **new capture points**, not just a copy of an existing table — the single most important adjustment to the design's Phase 1.

**Platform facts the design guessed at.** `src/core/db/connection.ts` selects `bun:sqlite` under Bun and `better-sqlite3` under Node; Bun's bundled SQLite has no extension loading, so `tryEnableSqliteExtensions()` probes system `libsqlite3` paths and calls `Database.setCustomSQLite()` — without a system library, `sqlite-vec` silently no-ops (`src/modules/memory/embeddings/vec-store.ts:57-63`). Present: `nanoid` (no ULID), `@casl/ability ^6.8.0`, `sqlite-vec ^0.1.9`, `@orama/orama`, `gray-matter`. Absent: zstd, `worker_threads` in `src`, ONNX/transformers, an `engines` field; local Bun is 1.3.10. Only `ollama` and `openai` implement `embed()`. Capabilities: `supportsTools/Images/Streaming` on `ModelInfo`, `supportsIsolatedCompletion` on `AIProvider` (`src/modules/model/types.ts:240`, true only for claude-code); no `supportsHeadlessInvocation`. Scheduler: `maxConcurrent: 4` (`src/modules/scheduler/index.ts:66`), no CPU-budget pool.

### B.3 Conflicts — decided and justified

1. **`save_memory` as a model write tool vs. R2.** Retire the model-facing write entirely: remove the tool, rule 8 of `core-rules.ts:30-35`, the 12 persona allow-list entries, the `memory_maintenance` autonomy binding (`autonomy-policy.ts:130`), and the critic's use. Evidence: measured 0/24 invocations before F1; F1.2 proved CLI agents *narrate* saves they never make. The design's read-only `memory_search`/`memory_expand` replace it; the only human write is the UI "pin" (`user_flag`, feeds heavy-pass priority). `memory_block_write`/`write_team_memory` are run-scoped blackboards, not memory — they stay in the agent module.
2. **Model-decided writes (capture pipeline).** Today the model decides *what* (kind, title, summary, body) and `note-writer` writes it verbatim as durable markdown with no trust tier and no injection scan — the 2026-08-27 spec calls this "deterministic *when*, model-decided *what*". Under v2 the model's output is a *candidate*; arbitration decides. Resolution: keep the capture machinery as the model pass, insert arbitration between it and storage, and never write model prose to the vault. Also: the deterministic pre-pass must run when the model pass yields nothing — today 12/15 runs wrote nothing at all.
3. **Orama search module duplication.** Two retrieval stacks (`src/modules/search` Orama + JS brute-force `vector-index.ts`; memory FTS5 + `sqlite-vec`) and two embedding-discovery paths. Decision: memory never depends on Orama (research §10-6 agrees); the search module keeps it for code/docs/files. Its JS vector scan and gateway-bypassing discovery (`search/index.ts:57-75`) are search-module debt, off memory's critical path.
4. **Two authorization schemes.** CASL `MemoryEntry` gates REST; security-gate risk tiers gate tools; the MCP server inherits the API-key owner's role. Decision: with no model-side write tool, the tool surface collapses to two green-tier read tools; CASL gains `delete`/`purge` on `MemoryEntry` and `MemoryShareScope`/`MemoryShareGrant` subjects for R6 (decision point 13 stands). Drill-down tools always use the conversation's project scope, so role checks live on the REST/UI edge only.
5. **`kind` vocabulary vs. design tags.** `user|feedback|project|domain|reference` encodes *what the note is for*; design facets encode *where it came from*. Neither subsumes the other. Decision: (a) add `project_type` as both a `memory_tag` facet and a gist `scope_type` (the 0.8.18 `domain` inheritance and D1 depend on it — the design has no such level); (b) add gist `scope_type='global'` for `user`/`feedback` notes, `pinned=true`, `feedback` keeps `why`/`howToApply` as structured fields (design's gist has none — add a `structured_json` column or two nullable text columns); (c) keep `kind` as a `memory_tag` facet `tag_type='kind'` for UI filters and for D1's ordering. `reference` collapses to an ordinary topic-scoped gist.
6. **Vault markdown as store vs. SQLite-first.** Decision: SQLite (L0–L3) is the system of record for everything machine-captured; the vault remains (i) human-authored/Obsidian-edited notes, (ii) the data-port import target, (iii) an optional read-only mirror of pinned global gists (`eyas memory export --vault`). Every vault file is ingested into L0 as `source_type='document'` (partition `vault:<path>`, hash = `vault_index.file_hash`). Justification: files cannot give bi-temporal supersede, trust tiers, tombstones, crypto-shred or bounded tier-1 injection; the design's "vault unchanged" clause only holds once the vault stops being the capture sink.
7. **Orphan-GC / physical deletion vs. R5.** Retire; tombstones only.
8. **L0 compression vs. external-content FTS5 and the chat store.** `conversation_messages` must remain uncompressed for the chat UI; the design's compressed `memory_blob` means messages are stored twice. Decision: accept the copy (R5 requires memory-owned bytes that survive conversation deletion), index L0 with a contentless FTS5 at flush, and keep `conversation_fts` only until the new assembler replaces `related-work.ts` (§G-2).

## C. Migration plan for live data

Principles: additive schema (no `ALTER`/`DROP` of legacy tables during cutover); deterministic, re-runnable (`INSERT OR IGNORE` on derived ULIDs); real `occurred_at` (never the migration date); vault files untouched on disk; a feature flag `memory.engine: 'legacy' | 'v2'` selects read/write paths; the legacy tables stay read-only for one release.

**Identity.** Derive each migrated row's ULID deterministically: timestamp part = source `created_at` (ISO text → ms), random part = first 80 bits of `SHA-256('legacy:' + table + ':' + pk)`. Record lineage as `memory_link(link_type='migrated_from', from=memory_raw.id, to='<table>:<pk>')` — a new link type, nothing else in the design changes.

**Keep the vault readable/exportable.** Files are never rewritten by the migration. Post-cutover, `eyas memory export --vault [--scope global|project:<id>]` renders current pinned gists and facts as frontmatter markdown (same `frontmatter.ts` schema, plus `memory_id`), so Obsidian users lose nothing; the mirror is one-way and marked `generated: true`.

Tested in Phase 1 against the migrated store: row counts equal, every `content_hash` unchanged, spot-check hashes match the source tables.

**Rollback.** (1) A disaster-recovery backup before migration [module exists; CLI surface unverified]; (2) new tables are additive, namespaced `memory_*`; (3) `memory.engine='legacy'` restores the old paths untouched until release N+1; (4) `eyas memory migrate --undo` drops only the new tables and `migrated_from` links; vault files were never touched. Flag default → `v2` in release N; legacy code and tables deleted in N+1.

## E. Risks specific to this migration and codebase

1. **Boot-order fragility.** `ModuleLoader.resolveDependencies()` orders by hard deps only (`src/core/module-loader.ts:52-72`); `memory` declares `dependencies: ['model']`, `optional: ['conversations','scheduler']` (`memory/index.ts:39-40`) and publishes at `onStart`. `agent/index.ts:979-988` reads `ctx.memory` non-lazily and works only because `bootstrap.ts` registers memory (217) before agent (238); new capture hooks in conversations (205), tools (235) and event-store (316) straddle memory. *Mitigation:* a lazy `ctx.memoryIngest` accessor backed by a bounded in-process queue that flushes at memory's `onStart` (L(−1) semantics); a regression test in the style of `conversations/memory-hooks-lazy`; fix `agent/index.ts:979` in the same wave.
2. **Prompt-budget exemptions.** Today's memory blocks sit outside prompt-wizard's `SectionBudget` because the 8 400-token prefix is fully allocated; `CORE_IDENTITY` overruns 491/200 tokens (documented, unfixed); `memory-context` can shrink to zero. The design's 900–1 600 tokens will land on top unless declared. *Mitigation:* one per-turn section with a declared reserve (default 1 200 tokens, §G-11) registered in `SectionBudget`; view 4 shows the real total; settle the `CORE_IDENTITY` overrun in the same change.
3. **CLI providers do not execute registry tools.** F1.2 proved live that CLI agents narrate tool calls they never make (`tool_executions`=0 after 12 runs). Drill-down `memory_search`/`memory_expand` may never be invoked on claude-code/grok/kimi runs. *Mitigation:* automatic injection must carry the full load — tiers 1–3 are designed for that; treat drill-down as a bonus, measure invocation rate in `memory_access_log`, and never rely on it for correctness (e.g. the critic must not mark a run incomplete for not calling it).
4. **Grok/kimi ACP bypass.** A grok session wrote to host memory despite three DENY events (`security_events` 307-309); ACP is cooperative; only claude-code closes the chain. *Mitigation:* extraction/consolidation/piggyback run only on providers with `supportsIsolatedCompletion && supportsHeadlessInvocation` (claude-code, API providers); ACP providers are chat-only for memory purposes; document the guarantee boundary in six languages; keep `deterministic-gate.ts` denies as detection, not enforcement.
5. **God Mode capture gap.** `routes.ts:693` returns its own stream before the capture call at `:1505`; 4 `god_mode_runs` exist with no memory trace. *Mitigation:* capture at `chatService.addMessage` and `agent_events` append (structural), which also covers background runs; add a regression test that a God Mode turn yields `memory_raw` rows.
6. **i18n parity.** Six new views × facets × trust labels × delete confirmations ≈ 150–250 new keys × 6 languages; the handbook is already out of parity (de/es missing ~7 sections). *Mitigation:* locale-key parity test in CI for `pages/memory/locales/*.json` (extend the existing duplicate-key check), handbook sections generated from one English source per wave, Klingon strings written with the same care as the others (the `tlh` lexical-upweight rule also needs a language detector that recognises it).
7. **Storage engine and extension loading.** Under Bun without system `libsqlite3`, `sqlite-vec` silently no-ops today; under `better-sqlite3`-on-Bun the native binary may not load on musl. *Mitigation:* Phase 0(b)/(h)/(i) on the real images; whichever engine wins, `eyas doctor` reports FTS5/vec0 availability and memory refuses to claim vector search it cannot run.
8. **Migration idempotency, timestamps, duplicates.** `conversation_messages.created_at` is ISO text vs. integer ms; ids are autoincrement; imported vault notes may also exist as episodic rows on other installs (data-port writes both). *Mitigation:* deterministic ULIDs from `(table, pk, created_at)`, `INSERT OR IGNORE`, content-hash dedup within partition, vault ingestion keyed on the existing `file_hash`, a dry-run on a copy of `data/sqlite/eyas.db` (Phase 0(j)) with counts + hash spot-checks as the gate.
9. **Two retrieval stacks during parallel operation.** *Mitigation:* `memory.engine` is exclusive; the SSE handler and `conversation-runner.ts` read one accessor.
10. **Scheduler contention and new infrastructure.** `maxConcurrent: 4`, no budget pool, no `worker_threads` anywhere in `src`, no zstd, no ONNX. *Mitigation:* Phase 0(e)/(f)/(h)/(k) numbers before Phase 2/4 commit; light pass in a worker with its own WAL connection; a per-job `cpuBudgetMs` hint the scheduler can honour later (decision point 6 deferred, not dropped); all additions Apache-2.0/MIT.

## G. Open decisions for the product owner (deduplicated; only those real for this codebase)

1. **Storage engine under Bun** (design #11). Options: keep `bun:sqlite` primary with the `setCustomSQLite` probe and hard-fail memory when extension loading is unavailable; or `better-sqlite3` under both runtimes. *Recommendation:* `better-sqlite3` under both if Phase 0(i) loads on the target images; otherwise keep `bun:sqlite` and make `eyas doctor` + the setup wizard require a system `libsqlite3` for vector search. *Consequence:* the first reverses `CLAUDE.md`'s stack priority and touches `connection.ts` for every module; the second leaves vector search install-dependent.
2. **L0 ownership of message bytes.** Options: `memory_raw` references `conversation_messages` (no copy, no immutability if a conversation is deleted); or memory keeps its own compressed copy (design). *Recommendation:* own copy; ~2× text storage is negligible at 1 KB/message. *Consequence:* `conversation_fts` becomes redundant for memory and can be retired with `related-work.ts`.
3. **Tool-result capture timing** (D3 revisit). Options: Phase 1 (hook the tool executor and stream events now) or Phase 1b/2. *Recommendation:* Phase 1b, immediately after messages, with an 8 KB cap and `ingested` trust; attachments deferred. *Consequence:* until 1b, L0 is text-only, exactly as D3 stated.
4. **Local embedder** (D5 revisit). Options: bundle transformers.js + int8 MiniLM (Apache-2.0, ~23 MB) as the default; or keep the provider bridge (ollama/openai) with FTS-only fallback. *Recommendation:* bundle, gated by Phase 0(e)/(k) numbers; provider bridge stays as an upgrade. *Consequence:* without it, every CLI-only install has no vector channel and the design's degraded mode is FTS-only, contradicting §4's "embeddings still run".
5. **Retire `save_memory` and the model-side write rule.** Options: retire now (Phase 1); or keep as a deprecated no-op that logs. *Recommendation:* retire now, replace rule 8 with "you cannot save memory; EYAS records automatically", keep a UI pin. *Consequence:* personas, prompts, autonomy policy, critic and MCP catalog all change in one wave; documented in six languages.
6. **Vault role.** Options: vault stays a capture sink (status quo); or human-authored + import + optional generated mirror (recommendation). *Consequence:* Obsidian users keep files; machine notes stop appearing as new markdown unless the mirror is enabled.
7. **Trust tier of imported ai-memory notes** (264 `reference`, `source:claude-code`). Options: `owner` (imported by explicit owner action) or `ingested` (model-written elsewhere). *Recommendation:* `owner` for data-port imports the owner performed, `ingested` for everything else; expose a bulk "trust" action in view 1. *Consequence:* `ingested` would down-weight the bulk of today's memory by 0.6 from day one.
8. **Add `project_type` scope and `global` pinned gists to the design** (D1/`domain` preservation). Options: extend the design's `scope_type`/`tag_type` enums; or flatten domain notes into project notes. *Recommendation:* extend. *Consequence:* schema and ranking tier 1 change before Phase 1 locks.
9. **Migration approach** (design #12). *Recommendation:* (b) — L0 backfill with real timestamps, L1/L2 via the queue, legacy tables read-only for one release, `--undo`. *Consequence:* R1 holds for pre-cutover history; extraction quality of old history arrives gradually.
10. **Access log placement.** Options: own `memory_access_log` (design) or the audit module. *Recommendation:* own table for high-volume inject/drilldown rows (10 % rank sampling); mirror mutations to `audit_entries`. *Consequence:* two places to look, but the audit retention job never truncates memory evidence.
11. **Injected-token reserve** (design #1) and the budget overrun. Options: 900 / 1 200 / 1 500 tokens declared in `SectionBudget`; raise the prefix reserve to 9 000 to also fix `CORE_IDENTITY`. *Recommendation:* 1 200 declared per-turn, reserve 9 000. *Consequence:* every agent's other sections shrink slightly on small-context models; view 4 makes it visible.
12. **`memory_blocks` and `team_memory` fate.** *Recommendation:* retire `memory_blocks` (0 rows, unreachable from personas); `team_memory` stays a run blackboard in the agent module, its promotion writes L0 + a task gist. *Consequence:* Letta-style blocks are gone; if wanted later they are a pinned `global`/`agent` gist.
13. **Piggyback default** (design #4) and heavy-pass budget for no-API-key installs (design #3). *Recommendation:* piggyback OFF by default — claude-code is headless already, ACP providers cannot be isolated (F1.3) or enforced (F1.6), so there is no provider on which the mechanism is both needed and safe; heavy-pass model budget 0 until a capable provider is configured, then an onboarding prompt. *Consequence:* installs with only grok/kimi stay at heuristic quality, disclosed in the UI.
