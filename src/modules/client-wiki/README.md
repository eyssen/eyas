# Client Wiki Module

Per-client (or per-project) auto-maintained knowledge base. Inspired by Devin's DeepWiki feature.

## Purpose

Each client or project has a living wiki, updated by both humans and background agents from:

- Codebase structure (future: AST indexer integration)
- Recent PRs and design decisions
- Stored conversations + chatter messages
- Customer communications

This phase (Phase 4E) delivers:

- Schema (pages + revisions + links)
- Service with CRUD, search, history, backlinks
- HTTP API under `/api/v1/client-wiki/`
- A safe server-side markdown renderer
- A frontend stub page

The auto-update agent writes a project-scoped page when a board ticket enters a closed stage, and when a team session records findings/decisions. Path templates are `ticket-<id>` and `decision-<id>` — the wiki row is already keyed by project id (`client_id`); slugs do not carry a client or organisation name. Projectless sessions still promote to the vault. Auto-update never copies vault notes onto the wiki.

## Data model

```
client_wiki_pages       Per-client markdown page, one row per slug
client_wiki_revisions   Append-only revision history (page_id, ts, content)
client_wiki_links       Directed page-to-page links (reference | mentions | depends)
```

A page is uniquely identified by `(client_id, slug)`. `client_id` is the project id.

## API

All routes use CASL `requirePermission` middleware on the `ClientWikiPage` subject.

| Method | Path                                                                  | Permission                    |
| ------ | --------------------------------------------------------------------- | ----------------------------- |
| GET    | `/api/v1/client-wiki/:clientId/pages`                                 | `read` `ClientWikiPage`       |
| GET    | `/api/v1/client-wiki/:clientId/pages/:slug`                           | `read` `ClientWikiPage`       |
| GET    | `/api/v1/client-wiki/:clientId/pages/:slug/history`                   | `read` `ClientWikiPage`       |
| GET    | `/api/v1/client-wiki/:clientId/pages/:slug/backlinks`                 | `read` `ClientWikiPage`       |
| GET    | `/api/v1/client-wiki/:clientId/search?q=...`                          | `read` `ClientWikiPage`       |
| POST   | `/api/v1/client-wiki/:clientId/pages`                                 | `create` `ClientWikiPage`     |
| PUT    | `/api/v1/client-wiki/:clientId/pages/:slug`                           | `update` `ClientWikiPage`     |
| DELETE | `/api/v1/client-wiki/:clientId/pages/:slug`                           | `delete` `ClientWikiPage`     |

`GET /pages/:slug?render=html` returns `{ ...page, html }` with server-rendered HTML.

## Markdown rendering

`markdown-render.ts` is a small, self-contained converter. Raw HTML is escaped, `javascript:` /
`data:` / `vbscript:` URL schemes are blocked. Supported features: ATX headings, GFM fenced
code blocks, GFM tables, ordered/unordered lists, bold/italic/inline code, links, paragraphs,
horizontal rules.

For richer client-side rendering, the frontend may swap this for Streamdown/remark. The server
keeps the minimal converter for safe server-side preview and summary extraction.

## Auto-update agent

`createWikiAutoUpdate` (wired in `onStart`). **Default off** — a project must
opt in on the project form (`wikiAutoTickets` / `wikiAutoDecisions`).

1. **Tickets.** Subscribes to `eyas.conversations.stage_changed`. A card entering
   a closed stage upserts `ticket-<conversationId>` only when `wikiAutoTickets`
   is on. Body: `title` (default) | `latest` | `transcript`.
2. **Decisions.** `promoteTeamSession` writes `decision-<sessionId>` only when
   `wikiAutoDecisions` is on. Otherwise (or with no effective project) it calls
   the vault promoter. One destination, never both.
3. **Human edits.** HTTP PUT without `autoGenerated: true` takes ownership
   (`autoGenerated = false`). Later auto-updates skip that page.
4. **Catch-all project.** `general-general` is treated as no project — no wiki page,
   even if the flags are on.
5. Wikilink maintenance (`addLink`) is still left to a later pass.

## Permission seeding

To wire this module into CASL roles, add the following subject grants in
`src/modules/permissions/roles.ts`:

```ts
// Admin
can('manage', 'ClientWikiPage')
// User
can('read', 'ClientWikiPage')
can('create', 'ClientWikiPage')
can('update', 'ClientWikiPage')
```

This is intentionally left to the central permissions module rather than self-seeded from here,
matching the pattern of `KnowledgePage` and `Document`.
